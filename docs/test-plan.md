# План тестування — Система керування студентським розкладом

Версія 0.1, віха M1. Основа — технічне завдання, вимоги ФВ-1 – ФВ-8.

## 1. Мета і обсяг

Перевірити, що прототип v0.1 виконує обов’язкові функціональні вимоги віхи M1: предмети, студенти, запис на предмети, розклад з перевіркою конфліктів, оцінки, консольний інтерфейс і обробку помилок.

Не входить у M1: ФВ-1.4, 2.4, 3.4, 4.8 — віха M2, ФВ-8 — віха M3.

## 2. Підхід

| Рівень | Що перевіряється | Інструмент |
|-|-|-|
| Модульні тести | Класи `Lesson`, `DefaultSchedule`, `DefaultScheduleManagementSystem`, `ConsoleApp` окремо від решти програми | JUnit Jupiter 6, модуль `tests` |
| Ручні тести | Сценарії користувача в консольному меню | `gradlew :app:run` |
| Регресія | Повторний запуск усіх модульних тестів перед кожним злиттям у `dev` | `gradlew build` |

Для кожної вимоги перевіряються позитивний сценарій і хоча б один негативний: дублікат, неіснуючий об’єкт, межові значення, конфлікт.

## 3. Середовище

Windows 11, Java 21, Gradle 9.7.1 через wrapper, IntelliJ IDEA. Дані в пам’яті, кожен тест створює новий екземпляр системи в `@BeforeEach`.

## 4. Критерії

- **Початок тестування:** модуль `app` злито в `dev`, `gradlew build` компілює проєкт.
- **Завершення M1:** усі автоматизовані тест-кейси проходять, ручні сценарії TC-M1 – TC-M3 виконано без критичних дефектів.
- **Дефект:** створюється issue з міткою `bug`, картка на дошці отримує стан `Помилка`.

## 8. Віха M3 — модульні тести незалежних класів

Після рефакторингу під впровадження залежностей (issue #20) класи модулів `core` і `app` поділено на незалежні й залежні. Незалежні тестуються напряму, без підміни класів. Залежний клас `DefaultScheduleManagementSystem` отримує розклад через конструктор, тому в тесті йому передається справжній `DefaultSchedule`. Підміна залежностей mock-об’єктами — віха M5.

Номери TC-24 – TC-30 зарезервовано за віхою M2.

## 9. Віха M5 – модульні тести з mock-об’єктами

Бібліотека макетів – Mockito 5.24.0 з розширенням `MockitoExtension` для JUnit Jupiter. Покриття коду – JaCoCo 0.8.16, звіт будує задача `gradlew :tests:jacocoTestReport` для класів модулів `core` і `app`. Номери TC-43 – TC-67.

### 9.1. Класи, що тестуються з макетами

| Клас | Що підміняється макетом | Що перевіряється |
|-|-|-|
| `DefaultScheduleManagementSystem` | `Schedule` – залежність, отримана через конструктор у віхі M3 | Які виклики й з якими даними система робить до розкладу, чи передає вона помилки розкладу без змін, чи не звертається до розкладу там, де не повинна |
| `ConsoleApp` | `ScheduleManagementSystem` і `Schedule`, отриманий через `getSchedule()` | Що введені користувачем значення доходять до системи без пробілів і в правильному порядку, як виводяться результати й помилки системи |

Об’єкти-значення `DefaultSubject`, `DefaultStudent`, `Lesson` не підміняються – тести створюють справжні екземпляри.

### 9.2. Класи-обгортки

- `ConsoleSession` – обгортка над `Scanner` і `PrintStream` для `ConsoleApp`. Приймає рядки введення, повертає весь вивід одним рядком з нормалізованими кінцями рядків.
- Обгортка над справжнім `DefaultSchedule` – `mock(Schedule.class, delegatesTo(new DefaultSchedule()))`. Усі виклики виконує справжній розклад, а Mockito рахує їх для `verify`. Використовується в TC-50.
